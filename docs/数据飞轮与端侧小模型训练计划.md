# 数据飞轮改造与端侧超小模型训练计划

> 对应代码：`recast/app`（Phase 1 web 原型）
> 本次重点：改写提示词与成功率、端侧数据飞轮、后续手机本地小模型路线

---

## 0. 一句话结论

这次把「改写」从一次性的提示词调用，改造成了一条**可验证、可重试、可积累**的生产线：

1. **改写提示词 v2**：显式允许并强制要求「从已有事实中读出它已经暗示的东西」，并把重构固化成结构化字段 `reconstruction.criterion/line`，模型不能再靠「只换人称」蒙混。
2. **确定性校验 + 机械修复**：语言、人称、长度先由本地规则检查；语言/人称漂移走一次轻量修复，不把基础设施问题伪装成「改写失败」。
3. **重试反馈**：重试时把上一稿和未命中的判据带回请求，避免「换一句引导语、产出几乎一样的文字」。
4. **本地数据飞轮**：每次尝试都按统一 schema 留在本机，自动派生 SFT 正例与偏好对，可脱敏导出 JSONL；默认关闭、可随时清空。
5. **为端侧小模型准备数据口径**：只让「真实模型 + 通过质检 + 用户归档」进入 SFT；只让「同一原文下后一次通过、前一次被拦」进入偏好对。demo 桩数据永不进入训练集。

## 1. 改写成功率：问题诊断与提示词改造

### 1.1 旧版的实际问题

用 DeepSeek `deepseek-flash` 对 4 条中文/英文日记样本跑了旧版提示词，观察到四类失败：

| 问题 | 表现 | 后果 |
|---|---|---|
| 只换人称 | 原文逐句替换「我 → TA」 | 质检五条全灭，用户觉得工具没在处理自己的输入 |
| 拒绝推断 | 模型把「不添戏」理解成「不能加任何一句新话」 | 事件复述完整，但没有重构落点 |
| 人称漂移 | 内心独白、所有格漏改（「我妈」「why am I…」） | 结构预检拦截，或读起来像半成品 |
| 语言漂移 | 中文原文偶发返回英文 | 直接不可用 |

旧版质检也有校准问题：有时把「结尾又回到同一句自责」判成 insight，有时又把真正的因果重构判成未命中。

### 1.2 新版提示词做了什么

`app/src/model/prompts.js`（`rewrite-v2.0` / `critique-v2.0`）：

- **授权推断，并给出落点**：明确写「推断是被允许且必需的；你不是在发明事件，而是在命名已有事实已经暗示的东西」，并给出五种重构的句首模板（insight / meaning / causal / closure / action）。这一步是成功率提升的最大来源——模型从「不敢加」变成「知道加哪一句」。
- **结构化重构**：输出从 `{rewrite, warmth}` 变为 `{rewrite, warmth, reconstruction: {criterion, line}}`。`line` 必须是成稿中的原句、且不能是原文句子的复制。运行时用确定性规则校验它是否真的出现在成稿里。
- **人称与语言锁死**：内心独白和所有格也要第三人称化；输出语言必须等于原文语言；中文原文的 warmth 与 `line` 也必须是中文。
- **长度写成硬数字**：提示词上限 1.6×（空白不计），工程侧仍保留 2.2× 的保守硬拦截。实测旧版「约 30%」经常被忽略。
- **质检判据可操作化**：因果允许解释「为什么这件事一直抓着 TA」，不要求五条全中；单句可以同时满足多条；每条 `why` 必须引用本次改写的原话。
- **重试反馈**：`session.js` 把上一稿 + 未命中判据装配成 `feedback.previous` 胶囊，明确要求「不要重复或轻微改写上一稿，必须新增一句可核对的重构」。

### 1.3 流水线

```text
原文 + 视角 + 引导语 (+ 上一稿反馈)
        │
        ▼
[1] 改写调用（temperature 0.4，JSON）
        │
        ▼
[2] 机械修复（仅语言/人称漂移；temperature 0.2）
        │
        ▼
[3] 确定性预检：语言 / 人称残留 / 长度比
        │   └─ 结构性问题直接短路，不花质检调用
        ▼
[4] 质检调用（temperature 0.2，JSON，五条判据）
        │
        ▼
{ distanced, warmth, critique, quality, reconstruction }
        │
        ▼
[5] 本地飞轮记录（可关闭）
```

### 1.4 小样本对照

同一批日记样本，单次生成（不代表统计显著，只说明方向）：

| 用例 | 旧版 | 新版 |
|---|---|---|
| 中文·项目评审 / 「为什么」 | 通过 2 条判据 | 通过（insight） |
| 中文·项目评审 / 「说明了什么」 | 通过 3 条判据 | 通过（insight） |
| 中文·等消息 / 「为什么」 | **未通过（字面复述）** | 通过（insight，新增「把沉默当成犯错证据」） |
| 中文·家人催工作 / 「因果链」 | 未测 | 通过（insight，新增「循环」句） |
| 英文·项目评审 / 「为什么」 | 通过 4 条判据 | 通过（meaning/causal/closure） |

工程侧同时观测到：新版 5/5 用例人称残留为 0、语言匹配 5/5、长度比 1.34–1.54，`reconstruction.line` 全部出现在成稿中且未复制原文。

**需要老实说明**：这是 5 条样本的探索性对照，不是评测集。真正的成功率要用飞轮积累的 held-out 样本持续测（见第 4 节）。

## 2. 本地数据飞轮：改造内容

### 2.1 设计目标

不是「埋点」，而是**为端侧小模型准备可复现的训练语料**：

- 能回答「这一次为什么通过 / 为什么被拦」；
- 能区分「模型生成得好」与「用户最终接受了」；
- 能构造 SFT 正例和偏好对；
- 全程本地、可见、可删、可导出；
- 每条样本带 prompt / critique 版本，提示词迭代后仍能追溯。

### 2.2 采集点

在 `session.runEngine()` 成功拿到结果后立即记录：

```js
recordAttempt({
  text, intensity, band, lens, guidance, attempt, prevId, result
})
```

`prevId` 形成重试链；用户动作在 `RecastView` 里补齐：

| 用户动作 | 标签 | 训练用途 |
|---|---|---|
| 点击归档 | `accepted` | SFT 正例候选 |
| 点击「换引导语重试」 | `retried` | 作为偏好对的 rejected |
| 三次未通过转支持路径 | `exhausted` | 负例 / 难例池 |
| 没有操作就离开 | `pending` | 中性，不进入训练导出 |

### 2.3 三种产物

**① Event（原始事件）**

```json
{
  "id": "fw_...",
  "at": "2026-11-09T...",
  "schema": "recast.flywheel.v1",
  "promptVersion": "rewrite-v2.0",
  "critiqueVersion": "critique-v2.0",
  "engine": "model",
  "model": "deepseek-flash",
  "prevId": "fw_...",
  "input": {
    "text": "...",
    "lang": "zh",
    "chars": 273,
    "intensity": 8,
    "band": "high",
    "lens": "future",
    "lensName": "未来的自己",
    "guidance": "为什么会出现这种情况？",
    "attempt": 1
  },
  "output": {
    "rewrite": "...",
    "warmth": "...",
    "reconstruction": { "criterion": "insight", "line": "..." }
  },
  "critique": {
    "passed": true,
    "findings": [{ "id": "insight", "hit": true, "why": "..." }]
  },
  "quality": {
    "languageMatch": true,
    "residue": 0,
    "ratio": 1.38,
    "lineInRewrite": true,
    "lineCopied": false,
    "repaired": false
  },
  "user": { "decision": "accepted", "at": "..." }
}
```

**② SFT 对**（`recast.sft.v1`）

筛选条件：`engine === 'model'`、`critique.passed`、`user.decision === 'accepted'`、有成稿。  
demo / 桩数据一律排除。

```json
{
  "id": "fw_...",
  "schema": "recast.sft.v1",
  "lang": "zh",
  "promptVersion": "rewrite-v2.0",
  "messages": [
    { "role": "system", "content": "You are the rewriting engine inside Recast..." },
    { "role": "user", "content": "Rewrite this entry now ...\n\nThe entry ..." }
  ],
  "response": "{\"rewrite\":\"...\",\"warmth\":\"...\",\"reconstruction\":{...}}"
}
```

**③ 偏好对**（`recast.preference.v1`）

同一原文、相邻两次尝试：后者通过 / 被归档，前者被拦。用于 DPO / ORPO，教小模型「哪种重构更好」，而不只是模仿正例。

```json
{
  "id": "fw_a->fw_b",
  "schema": "recast.preference.v1",
  "lang": "zh",
  "promptVersion": "rewrite-v2.0",
  "input": { "original": "...", "lens": "future", "guidance": "..." },
  "chosen":   { "rewrite": "...", "reconstruction": {...}, "critique": {...} },
  "rejected": { "rewrite": "...", "reconstruction": {...}, "critique": {...} }
}
```

### 2.4 隐私与安全边界

| 约束 | 实现 |
|---|---|
| 默认关闭 | `flywheel.enabled = false`，设置页显式开启 |
| 只在本机 | 只写 `localStorage`，没有任何上传请求 |
| 导出可脱敏 | 默认遮罩邮箱、手机号、URL、疑似长证件号 |
| 不含敏感凭证 | 不存 API Key / Base URL；量表分数、分层、复核记录也不进入飞轮 |
| 可删除 | 飞轮页「删除训练数据」立即清空；设置页「清除本机全部数据」也会连带清空并关闭开关 |
| 容量上限 | 2000 条；超出优先丢弃最旧的未归档 / 非配对样本 |
| 可追溯 | 每条带 `promptVersion` 与 `critiqueVersion` |

### 2.5 页面入口

- 顶栏新增 `Flywheel`（中文「数据飞轮」）
- `/flywheel`：开关、统计、按语言/视角/重构类型的分布、三种 JSONL 导出、删除
- `/settings`：飞轮状态与小入口，符合「可见、可控」的既有原则

## 3. 端侧超小模型训练计划

### 3.1 目标

在手机本地跑一个 **0.3B–1.5B** 的改写模型，完成：

- 输入：第一人称日记（中文 / 英文）
- 输出：第三人称 + 一次重构 + 温度层（JSON）
- 约束：断网可用、单次延迟可接受、内存可控、不把原文发到云端

它不替代质检与安全分流；它是「没有 Key / 不想联网」时的本地改写候选。

### 3.2 候选底座

| 规模 | 候选 | 量化后大致体积 | 适合 |
|---|---|---|---|
| 135M–360M | SmolLM2-135M/360M、Qwen2.5-0.5B | 80–350 MB | 极低端机、先验证链路 |
| 0.5B–0.8B | Qwen2.5-0.5B-Instruct、Qwen3-0.6B、MiniCPM-0.5B | 300–550 MB | 主力候选 |
| 1B–1.5B | Gemma 3 1B、Qwen2.5-1.5B、MiniCPM-1B | 600 MB–1 GB | 中高端机、质量优先 |

优先顺序：**先 0.5B 级别验证数据与训练配方，再决定是否上 1.5B**。手机内存比模型参数更早成为瓶颈：Q4 量化 + 512–1024 token 上下文 + KV cache，留给系统的余量要足够。

### 3.3 数据配方

建议从飞轮导出后做三阶段训练：

**阶段 A：拒绝采样 SFT（冷启动）**

- 来源：真实模型 + 通过质检 + 用户归档
- 目标量：**1000–3000 条**；中英各半；每个视角至少 100 条
- 去重：按原文的规范化哈希去重；同一原文最多保留 2 条不同重构
- 质量过滤：`residue = 0`、`languageMatch = true`、`lineInRewrite = true`、`lineCopied = false`、长度比 ≤ 1.8
- 训练方式：LoRA / QLoRA，rank 8–16，学习率 1e-4 量级，1–3 epoch
- 注意：只学「改写 + 温度」输出，不把质检的 judge 文本混进目标

**阶段 B：偏好优化（校准「什么叫重构」）**

- 来源：飞轮偏好对
- 目标量：**300–1000 对**；先按语言分层，再按视角分层
- 方法：DPO / ORPO / SimPO（0.5B 级别优先 ORPO，省掉参考模型显存）
- 过滤：chosen 必须通过质检；rejected 必须被明确拦截；两边长度差不要超过 2×
- 目的：让小模型避免「只换人称」「自我批判」「结尾说教」这些失败模式

**阶段 C：蒸馏与加固（可选）**

- 用更强的教师模型（DeepSeek / 更大本地模型）在**未标注的新日记**上生成候选
- 用同一套质检 + 人工抽检做拒绝采样，补充长尾场景
- 小模型学会「先内部决定 criterion，再写一句落点」的隐式流程；如果底座支持，可保留 `reconstruction` 字段做可解释性

### 3.4 训练与部署链路

```text
手机/Web 本地飞轮
   │  用户主动导出 JSONL（脱敏）
   ▼
训练工作站
   │  数据清洗 / 去重 / 分层 / 过滤
   │  LoRA SFT → 偏好优化 → 合并
   ▼
量化导出
   │  GGUF Q4_K_M（llama.cpp）
   │  或 ONNX / Core ML / MLC
   ▼
Tauri 2 移动端
   │  本地推理，无网络
   ▼
飞轮继续记录「本地模型 vs 云端模型」的输出与用户决定
```

- **运行时**：Android 优先 llama.cpp（GGUF）；iOS 可走 llama.cpp 或 Core ML / MLC，按实测延迟定。
- **模型管理**：模型文件按版本号存放，支持灰度、回滚；首版不自动下载大模型，随安装包或用户主动导入。
- **回退策略**：本地模型连续失败 / 超时，回退到用户配置的 BYOK 云端模型；两条路径共用同一质检门。
- **提示词一致性**：端侧模型的 system prompt 必须使用与飞轮导出相同的 `rewrite-v2.0` 模板，否则训练/推理分布不一致。

### 3.5 评测

固定一套 held-out 评测集（不来自训练用户）：

- 规模：**200–500 条**，中英各半，覆盖 high/mid 强度与四种视角
- 自动指标：
  - 五条判据的通过率（任一条命中即通过）
  - 人称残留率（目标 0）
  - 语言匹配率（目标 ≥ 99%）
  - 长度比分布（目标 0.8–1.6）
  - JSON 可解析率（目标 ≥ 99%）
- 人工指标：
  - 「是否只换人称」二元判断
  - 「是否编造事件」二元判断
  - 「温度层是否变成说教 / 承诺」二元判断
- 安全红线：
  - 危机内容必须仍走本地分诊 / 转介，不交给改写模型
  - 不输出诊断、治疗建议、价值评判
- 通过标准（建议初版）：
  - 相对教师模型通过率 ≥ 80%
  - 只换人称率 ≤ 5%
  - 编造事件率 ≤ 2%
  - 语言/人称结构错误 ≤ 1%

### 3.6 飞轮闭环

```text
采集（每次尝试）
  → 标注（用户重试 / 归档 / 放弃）
  → 导出（SFT / 偏好对）
  → 训练（LoRA + 偏好优化）
  → 评测（固定 held-out + 安全红线）
  → 部署（端侧量化模型）
  → 继续采集（本地 vs 云端对照）
```

每轮只改一个变量（提示词 / 数据配比 / 底座 / 量化），否则无法归因。

## 4. 风险、边界与诚实说明

1. **数据自选择偏倚**：愿意开启飞轮、愿意归档的用户不代表全部用户。导出时要保留 `engine`、`lens`、`intensity` 等字段，训练与评测都按层报告，不只报总体。
2. **小模型更容易「顺从」**：0.5B 级别可能更倾向于复述或说教。偏好对与质检过滤是必要的，但不能替代人工抽检。
3. **隐私不是口号**：飞轮默认关闭、导出默认脱敏、删除即删除；如果未来做跨用户聚合，必须另做差分隐私 / 联邦聚合设计，不能把当前 JSONL 直接上传。
4. **合规**：仍定位为自我觉察工具，不是医疗器械。端侧模型不能做诊断；危机路径不依赖模型。
5. **样本量**：5 条探索性对照不能证明「成功率提升 25 个百分点」。真正的结论要等飞轮积累到几百条、并用固定评测集复测。

### 本地验证

```bash
cd recast/app
npm install
npm run dev
# http://localhost:5173/#/flywheel
```

建议验证顺序：

1. 打开 `/flywheel`，开启采集；
2. 用演示模式跑一次「失败 → 重试 → 通过 → 归档」，确认 Attempts 增加、SFT 仍为 0（demo 被排除）；
3. 在 `/settings` 填入自己的 Key，跑一次真实改写并归档，确认 SFT +1；
4. 导出 SFT / 偏好对 / 原始 JSONL，检查脱敏与字段；
5. 点「删除训练数据」，确认本机清零。
